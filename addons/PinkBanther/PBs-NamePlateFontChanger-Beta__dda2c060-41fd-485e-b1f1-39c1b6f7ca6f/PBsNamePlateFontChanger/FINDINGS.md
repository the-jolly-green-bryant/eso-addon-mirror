# 頭上ネームタグ（nameplate）に対して何ができるか — 調査結果

調査対象: `esoui/esoui`（live ブランチ、ゲームクライアント本体の Lua ソース + `ESOUIDocumentation.txt`）

## 結論

**「称号名 / キャラクター名 / \<ギルド名\>」の3行レイアウトへの組み替えは、アドオンからはできない。**

頭上のネームタグはエンジン（C++）が描画している。クライアントの Lua ソース全体を検索しても、
ネームタグの文字列を組み立てている箇所・レイアウトしている箇所・コントロールは一切存在しない。

- `grep -ri nameplate` で Lua 側にヒットするのは **設定画面の項目名だけ**
  （`esoui/pregameandingame/zo_options/`、`esoui/lang/*_client.lua` の設定ラベル）。
- 描画側のコード・XML テンプレートは存在しない。つまりフック対象がない。

## Lua から触れる範囲（ネームタグ関連 API の全て）

| API | 内容 | ドキュメント上の扱い |
| --- | --- | --- |
| `SetNameplateGamepadFont(fontName, fontStyle)` / `Get...` | ネームタグの**書体と縁取りスタイル** | private 表記なし |
| `SetNameplateKeyboardFont(fontName, fontStyle)` / `Get...` | 同上（KBM 側） | private 表記なし |
| `GetSetting(SETTING_TYPE_NAMEPLATES, ...)` | 表示設定の読み取り（称号表示 / ギルド表示 / 全体 ON-OFF など） | 読みは可 |
| `SetSetting(SETTING_TYPE_NAMEPLATES, ...)` | 同 書き込み | **ドキュメントは public 扱いだが、実際は private**（PB's ChatAssistant で実測済み） |
| `EsoStrings[SI_NAMEPLATE_SECOND_LINE_FORMAT]` | 2行目（ギルド行）の書式 `"<<<1>>>"` | Lua 文字列テーブル |

重要な点:

- **フォントサイズの引数がない。** サイズを通せるとすれば ESO のフォント記述子の書き方
  （`"パス|サイズ"`）に載せる場合だけ。ドキュメントからは判定できない → 実測が必要。
- **1行目（称号＋キャラクター名）の書式文字列は存在しない。** `SI_PLAYER_NAME_WITH_TITLE_FORMAT`
  は Lua UI 用（`zo_primaryplayername.lua`）で、ネームタグは使っていない。
  称号が名前の前に出るか後ろに出るかはサーバー側の称号データ由来と思われる。
- `SI_NAMEPLATE_SECOND_LINE_FORMAT` は **ギルド行専用**。ここに称号や名前は渡ってこない。
  しかも esoui 内で一度も読まれていないため、エンジンが自前の文字列テーブルを見ている
  可能性が高い（＝ Lua 側で上書きしても画面は変わらない公算が大きい）。要実測。

## 自前で頭上ラベルを描く案（3行レイアウトの唯一の代替）

3D レンダースペースを使えば自作ラベルをワールド座標に置ける
（`Create3DRenderSpace` / `Set3DRenderSpaceOrigin` / `WorldPositionToGuiRender3DPosition`、
OdySupportIcons と同じ手法）。ただし致命的な制約が二つある。

1. **対象を列挙できない。** ワールド座標を取れるのは unitTag があるユニットだけ
   （`player` / `group1..group24` / `reticleover`）。周囲を歩いている非パーティのプレイヤーを
   列挙する API は存在しない → 「各キャラクターの頭上」は実現できない。
2. **ギルド名を取得する API がない。** `GetGuildName(guildId)` は自分の所属ギルド用。
   他プレイヤーがネームタグに出しているギルド名を取る手段がない → 3行目が作れない。

さらに、自作ラベルを出しても**標準のネームタグを消せない**（`SetSetting` が使えないため、
プレイヤーが手動で設定を切る必要がある）。二重表示になる。

## 実測が必要な残りの不明点（probe ビルドで確認する）

1. `SetNameplateGamepadFont` はアドオンから呼べるか（private ではないか）
2. `"フォントパス|サイズ"` でサイズが通るか
3. `SetSetting(SETTING_TYPE_NAMEPLATES, ...)` は本当に塞がれているか
4. `SI_NAMEPLATE_SECOND_LINE_FORMAT` の Lua 上書きが画面に反映されるか

# 実測結果（PS5 / api 101050 / jp / gamepadPreferred=true, probe 0.1.0）

| # | 項目 | 結果 |
| --- | --- | --- |
| 1 | `SetNameplateGamepadFont(same)` | **OK — アドオンから呼べる** |
| 2 | `SetNameplateKeyboardFont(same)` | **OK** |
| 3 | `GetNameplateGamepadFont()` | `$(GAMEPAD_MEDIUM_FONT)` / style `4` |
| 4 | `GetNameplateKeyboardFont()` | `$(BOLD_FONT)` / style `4` |
| 5 | `GetSetting(SETTING_TYPE_NAMEPLATES=0, ...)` | 読み取り可（all=1 / titles=1 / guilds=1） |
| 6 | `SetSetting(...)` | **private 確定**。`Attempt to access a private function 'SetSetting' from insecure code` |

## `pcall` は private 関数呼び出しを防げない

`SetSetting` は `pcall` 越しに呼んでいたが、**捕捉されずに UI エラーダイアログが出て、
実行中のチャンクごと落ちた**（probe の 7 行目以降が出力されなかった原因）。

つまり **「private かどうか分からないから試しに呼んでみる」ができない**。
private の疑いがある関数は呼ばずに、ドキュメントとソースから判断するしかない。

## これで確定したこと

- 標準ネームタグに対してアドオンができるのは **フォント（フェイス・スタイル・おそらくサイズ）の変更だけ**。
- 称号行・ギルド行の表示 ON/OFF は**プレイヤーが手動でゲーム設定を変える**しかない（アドオンからは不可）。

## 残る不明点

- `"$(GAMEPAD_MEDIUM_FONT)|32"` のように **サイズを記述子に載せて通るか**。
  ESO のフォント記述子は `フェイス|サイズ|スタイル`（`esoui/fontdefs/gamepad/defaultfontdefs_gamepad.xml`）
  なので形としては妥当。→ `/pbtag font 32` で実測する。
- `SI_NAMEPLATE_SECOND_LINE_FORMAT` の Lua 上書きが画面に反映されるか。→ `/pbtag guild test` で実測する。

## JP クライアントのフォント事情（`esoui/fontstrings/japanese/`）

`$(GAMEPAD_MEDIUM_FONT)` = `FTN57.slug`、CJK 用に `ESO_FWNTLGUDC70-DB` / `MYingHeiPRC-W5` が
バックアップフォントとして登録されている。**フェイスを生パスに差し替えると日本語が出なくなる**ため、
エイリアスは維持したままサイズだけを足すこと。

# 実測 2（probe 0.1.0 / `/pbtag font 32`）

**`"$(GAMEPAD_MEDIUM_FONT)|32"` でネームタグの文字サイズが実際に変わった。**

→ フォント記述子 `フェイス|サイズ` はエンジンのネームタグ経路でも解釈される。
サイズ引数を持たない `SetNameplate*Font` でサイズを制御できることが確定。

これにより 1.0.0 の機能範囲が確定した：

- 変更できる: **文字サイズ / 書体 / 縁取りスタイル**（全キャラクターのネームタグに適用）
- 変更できない: 行の並び順・改行・センタリング（エンジン描画）
- 変更できない: 称号行・ギルド行の表示 ON/OFF（`SetSetting` が private。ゲーム設定で手動）

## 未測定のまま残したもの

`SI_NAMEPLATE_SECOND_LINE_FORMAT` の Lua 上書き（`/pbtag guild test`）。
esoui 内で一度も読まれていないため、エンジンは自前の文字列テーブルを見ていると推測される
＝効かない公算が高い。設定項目にはせず、コマンドとしてのみ残してある。

# 追加検証：色は変えられるか／並び替えは本当に不可能か

## 文字の色 → 変更できない

- ネームタグの色は `INTERFACE_COLOR_TYPE_NAME_PLATE`（および `..._NAME_PLATE_HEALTH_START/END`,
  `..._NAME_PLATE_HIT_INDICATOR`, `..._NAME_PLATE_EFFECT_VISUAL_START/END`）として存在する。
- しかし API は **`GetInterfaceColor` のみ。`SetInterfaceColor` はドキュメント全体に存在しない。**
  グローバルな `Set*Color` 系は `SetChatCategoryColor` / `SetChatContainerColors` /
  `SetSCTEventVisualInfoTextColor` と、個別コントロールのメソッド（`SetColor` 等）だけ。
- 色はユニット種別ごと（`UNIT_NAMEPLATE_ALLY_GROUP` … の `UnitNameplateType` 列挙、
  Lua からは一度も参照されていない＝エンジン専用）にエンジンが決めている。
- 唯一の可能性はギルド行の書式文字列に `|cRRGGBB...|r` を仕込むこと。ただし下記のとおり未検証。

## 並び替え → 3つの方法で「無い」ことを確認した

### ① ネームプレート関連関数の全列挙

`ESOUIDocumentation.txt` 内で `Nameplate` / `Overhead` を含む関数は以下の4つのみ。

```
SetNameplateKeyboardFont / GetNameplateKeyboardFont
SetNameplateGamepadFont  / GetNameplateGamepadFont
```

### ② ネームプレート設定 `NAMEPLATE_TYPE_*` の全列挙（42項目）

表示ON/OFF、ヘルスバー、ハイライト、各種インジケーター、`SHOW_PLAYER_TITLES`、
`SHOW_PLAYER_GUILDS` のみ。**並び順・書式・改行に関する設定項目は存在しない。**

### ③ エンジン専用の書式文字列を総当たりで探索（決定的）

「1行目を組み立てる書式文字列がどこかにあるのでは」という仮説を機械的に潰した。

1. `en_client.lua` から**引数を2つ以上取るクライアント文字列**を抽出 → 786個
2. そのうち**ゲーム本体の Lua が一度も参照していないもの**（＝エンジンが直接使う候補）→ 199個
   （文字列定義ファイル `lang/` `*localization/` は除外して集計）
3. 199個のうち名前・称号・プレイヤー関連の語を含むもの → 43個

43個の中身はギルド履歴イベント、ツールチップ、Tribute のカード効果、PSN プレゼンス表示など。
**「名前＋称号」を組み立てる書式文字列は1つも無い。**

→ 1行目（称号＋キャラクター名）はクライアント文字列を経由せず、エンジンのコード内で
完結している。Lua から差し込めるポイントが無い。

ネームタグ関連で Lua に露出している文字列は `SI_NAMEPLATE_SECOND_LINE_FORMAT`
（ギルド行の `<<<1>>>`）ただ一つ。

## 未検証（残り1つ）

`/pbtag guild test` … `SI_NAMEPLATE_SECOND_LINE_FORMAT` の Lua 上書きが画面に届くか
`/pbtag guild color` … 届くなら、色マークアップも通るか

これが通れば「ギルド行の装飾と色」だけは可能になる。届かなければ、ネームタグに対して
アドオンができるのはフォント（大きさ・書体・縁取り）のみで確定。

# 追加検証：頭上からネームタグまでの間隔（垂直オフセット）

## 結論：調整できない

| 調べた場所 | 結果 |
| --- | --- |
| `Nameplate` を含む全関数 | フォント用の4つのみ。`NameplateOffset` / `Height` / `Scale` / `Distance` は存在しない |
| ネームプレート設定 `NAMEPLATE_TYPE_*`（42項目） | 位置・高さ・スケールの項目なし |
| `SETTING_TYPE_IN_WORLD` の `IN_WORLD_UI_SETTING_*` | グロー、同乗設定、装備の非表示など。頭上表示に関わるものなし |
| CVar | `GetCVar` / `SetCVar` は公開だが、クライアントが実際に使う CVar はログイン情報・ガンマ・デバッグ系のみ。ネームプレート関連の CVar は一つも参照されていない |

**存在しない CVar 名を推測して `SetCVar` を撃つことはしない。**
`SetSetting` と同じ失敗（ドキュメントに無い挙動を試して UI エラー）を繰り返すことになる。

## 間接的に見かけの間隔が変わりうるもの（未検証）

1. **文字サイズ** — アンカー点が固定でそこからテキストが伸びる方式なら、サイズ変更で
   見かけの隙間が変わる可能性がある。アンカーがブロック中心なら上下対称に広がるだけで変わらない。
   `/pbtag size 16` と `/pbtag size 48` を比べれば判別できる。
2. **行数** — ギルド行・称号行をゲーム設定で消せばブロックの高さが変わる。

# 書体エイリアスの実体（`esoui/fontstrings/`）

`$(...)` エイリアスが実際にどのフォントファイルに解決されるかは言語ごとに違う。

| エイリアス | 西欧版 | 日本語版 |
| --- | --- | --- |
| `GAMEPAD_MEDIUM_FONT` | FTN57 | FTN57（英数字）／日本語は ESO_FWNTLGUDC70-DB にフォールバック |
| `GAMEPAD_BOLD_FONT` | FTN87 | FTN87（英数字）／日本語は同上にフォールバック |
| `GAMEPAD_LIGHT_FONT` | FTN47 | ESO_FWNTLGUDC70-DB |
| `MEDIUM_FONT` | Univers57 | ESO_FWNTLGUDC70-DB |
| `BOLD_FONT` | Univers67 | ESO_FWNTLGUDC70-DB |
| `CHAT_FONT` | Univers57 | ESO_FWUDC_70-M |
| `ANTIQUE_FONT` | ProseAntiquePSMT | ESO_KafuPenji-M |
| `HANDWRITTEN_FONT` | Handwritten_Bold | ESO_KafuPenji-M |
| `STONE_TABLET_FONT` | TrajanPro-Regular | ESO_KafuPenji-M |

**日本語版は9つの名前の裏に実体が5種類しかない。**
ゴシック（ESO_FWNTLGUDC70-DB）、チャット用ゴシック（ESO_FWUDC_70-M）、
英数字用の FTN57 / FTN87、筆文字（ESO_KafuPenji-M）。

`<BackupFont>` 宣言により、英数字用フォントでも日本語部分は自動でゴシックに落ちる。
だから**エイリアスを使う限り日本語が消えることはない**。生パスを指定すると保証が外れる。

# 再検証：「デザイン要素をハードコードで持つとは考えづらい」への回答

指摘は正しい。**「ハードコード」という表現が不正確だった。**
正しくは「**エンジン側にあり、Lua に露出していない**」。ZOS 側ではデータ駆動である可能性は高い。
ただしそのデータはアドオンから到達できないので、結論は変わらない。

根拠を「見つからなかった」から「積極的な証拠」に入れ替える。

## ① ZOS 自身のネームプレート設定パネルの全内容

`esoui/ingame/optionspanels/optionspanel_nameplates_shared.lua`（473行）がネームプレート設定
画面の定義そのもの。公開されている項目は以下で全部：

- 表示条件（自分/パーティ/友好NPC/友好PC/中立NPC/敵NPC/敵PC × なし・ターゲット時・負傷時・常時）
- 各表示の減光（highlight/dimming）
- ヘルスバー（同カテゴリ分＋整列・チェイスバー・枠線）
- 同盟アイコン、パーティアイコン、蘇生アイコン、フォロワーアイコン、ターゲットマーカー
- グロー（ターゲット/インタラクト、強度・太さ）、ターゲットマーカーの大きさ

**文字レイアウト・並び順・オフセット・フォントの項目は一つもない。**
ZOS 自身がネームタグのレイアウトをユーザー向けの調整項目として持っていない。

さらに注目点：**ゲームの設定画面にはネームプレートのフォント項目すら存在しない**のに、
`SetNameplateGamepadFont` / `SetNameplateKeyboardFont` という API だけが公開されている。
ZOS が Lua に開けたのは「書体とスタイル」だけ、という意図的な線引きに見える。

## ② 決定的な制約はレンダリングではなく「データ」

仮に描画を完全に自作できたとしても、**描く中身が取得できない**。

- クライアントが使う unitTag は `player` / `group1..N` / `boss1..N` / `companion` /
  `reticleover` のみ。**周囲のプレイヤーを列挙する API が存在しない。**
- **他プレイヤーがネームタグに出しているギルド名を取得する API が存在しない**
  （`GetGuildName(guildId)` は自分の所属ギルド用）。

つまり自作ラベル方式は「フックが見つからない」のではなく「データが無い」で詰む。
唯一の例外はターゲット中の相手（`reticleover`）で、名前と称号は取れるがギルド名は取れない。

## ③ 称号はサーバーデータで、並び順はおそらく称号側にある

`en_client.lua` に `SI_TITLE1` 形式の称号文字列は存在しない（称号はサーバー由来のデータ）。
1行目を組み立てる書式文字列がクライアントに無い以上、
「称号が名前の前に出るか後ろに出るか」は**称号データ自体が持っている**と考えるのが自然。

これは測定可能。`/pbtag status` に以下を追加した：

```
player name=... title=...
GetTitle(index)=...
target name=... title=...      -- 誰かをターゲットしていれば
```

称号文字列に区切り文字や `<<1>>` スロットが含まれていれば、この推測が裏づけられる。
いずれにせよサーバーデータなので書き換えはできない。

## 否定しきれないこと（正直に）

エンジン側のデータファイル（Localize.xml やクライアントのバイナリデータ）に
レイアウト定義がある可能性は否定できない。esoui リポジトリは Lua/XML 層だけで、
エンジン本体は含まれていないため。ただしそこはアドオンから到達できない。
変えられるようにするには ZOS が API を追加する必要がある。

# 実測 3：ギルド行の文字列上書き → **効かない**

`/pbtag guild test`（`SafeAddString(SI_NAMEPLATE_SECOND_LINE_FORMAT, "[[<<1>>]]", 999)`）を実行しても
画面上のギルド行は変化しなかった。`GetString` の戻り値は変わるので、Lua 側のテーブルは
書き換わっている。つまり**エンジンのネームタグ描画は Lua の `EsoStrings` を見ていない**。

→ ネームタグの**文字列そのものは一切変更できない**ことが確定。
アドオンにできるのはフォント（大きさ・書体・縁取り）のみ。

この結果を受けて `/pbtag guild` コマンドと関連コードは 1.1.0 で削除した。

# 実測 4：書体変更でUIリロードが発生する

設定パネルで書体を変えると、その瞬間にUIの再読み込みが走る。文字サイズでは起きない。

## 原因

1. **こちらの実装の問題（修正済み）** — `Apply()` がゲームパッド用とキーボード用の
   **両方**に書き込んでいた。コンソールでは常にゲームパッド側しか描画に使われないのに、
   見えないキーボード側の書体まで変更していた。それだけでリロードの引き金になり得る。
2. **ゲーム側の仕様（回避不能）** — まだ読み込まれていないフォントに切り替えると、
   クライアントはフォント構築のためにUIを再読み込みする。

## 1.1.0 での対処

- **使われている側だけに書き込む**（`ActiveSlot()`）。コンソールではキーボード側に触らない
- **値が変わらないときは書き込まない**（`WriteSlot()` が `GetNameplate*Font` で読み戻して比較）。
  これは無駄なリロードを防ぐだけでなく、**ループの防止**でもある：
  フォントは `EVENT_PLAYER_ACTIVATED` ごとに再適用しており、無条件に書き込むと
  ゾーン移動のたびにリロード → リロードが次の activation を起こす → 無限ループになる
- `EVENT_GAMEPAD_PREFERRED_MODE_CHANGED` で、モードを切り替えたときに反対側へ適用
- 書体のツールチップに「再読み込みが起きること・サイズと縁取りでは起きないこと」を明記

# 不具合：縁取り設定が設定画面を開き直すと「デフォルト」に戻る（1.2.1 で修正）

表示自体は変わるのに、パネルを閉じて開くと選択が「デフォルト」に戻る。
書体（face）では起きない。両者の違いは**デフォルトを表す値**だった。

| 設定 | デフォルトを表す値 | 症状 |
| --- | --- | --- |
| 書体 | `""`（実在する文字列） | 正常 |
| 縁取り | `nil` | 開き直すと「デフォルト」表示に戻る |

`nil` は
「未設定」と区別できず、`accountDefaults` に入れられず（キーが存在しないのと同じ）、
`getFunction` が `nil` を返すとコンボボックスは選択対象を失って**先頭項目**を表示する。
先頭項目は「デフォルト」なので、症状と完全に一致する。

## ZO_SavedVars の確認（濡れ衣だった）

`esoui/libraries/utility/zo_savedvars.lua` を読んで確認した。
`CopyDefaults` は **defaults に無いキーを削除しない**（不足キーを補うだけ）。
インターフェースは `__index = current` / `__newindex` で素直に読み書きする。

→ `accountDefaults` に無い `originalGamepadFont` 等の退避データが消える心配はない。
保存機構は正常で、原因は `nil` を値として使っていたこちらの設計。

## 修正

- `addon.STYLE_INHERIT = -1` を導入。「クライアント既定のまま」を実在する値で表す
- `accountDefaults.style = addon.STYLE_INHERIT`（他の設定と同様、必ず存在するキーになる）
- `styleByValue[-1]` にデフォルト項目を登録し、`getFunction` が **nil を返さない**ようにした
- `BuildDescriptor` は `style == STYLE_INHERIT` のとき元のスタイルを使う
- 既存ユーザーの `style` 未設定データは、ロード時に `CopyDefaults` が `-1` を入れて自動移行される

# 不具合：ロード画面（エリア移動）でアドオンが無効化される

## 有力な仮説：リロードループ

1.2.1 までは `EVENT_PLAYER_ACTIVATED` の**たびに**フォントを適用していた。
`EVENT_PLAYER_ACTIVATED` はログイン時だけでなく**ゾーン読み込みのたびに発火する**。

- フォントの**書体**を書き込むと、クライアントはフォント構築のためUIを再読み込みする
- UI再読み込みは Lua 状態をリセットし、**再び `EVENT_PLAYER_ACTIVATED` を発生させる**
- したがって「毎回書き込みが必要と判断され続ける」状態はそのままリロードループになる

書き込み前に `GetNameplate*Font()` で読み戻して同値なら書かないガードは入れてあったが、
これは**クライアントが渡した文字列をそのまま返す場合にしか効かない**。
クライアントが記述子を正規化していたら（エイリアスを実パスに解決する、サイズ部分を落とす等）
比較は永遠に一致せず、activation のたびに書き込みが走る。**ここは未検証だった。**

## 1.3.0 の対策

### ① 適用はセッションで最初の1回だけ

`appliedThisSession` フラグを追加。ゾーン移動のたびの書き込みを止めた。
フォントはクライアント設定なので、ゾーン移動を跨いで残っていれば何もする必要がない。

### ② リロードをまたいで効く書き込み予算

セッション内カウンタでは無意味（リロードがカウンタごとリセットするため）。
カウンタを SavedVariables に置いた。リロードは SavedVariables をディスクに書き出すので、
**ループを跨いでカウントが残る**。

`WRITE_BUDGET = 4` / `WRITE_WINDOW_SECONDS = 120`。
超過したら書き込みを止め、チャットに理由を出す。

### ③ 読み戻しの一致を記録する

`diag.lastWritten` / `diag.lastReadBack` / `diag.readBackMatches` を SavedVariables に記録。
**推測していた「クライアントが記述子を正規化するか」を実測値として残す。**
`/pbfont status` で確認でき、アドオンが無効化されて再読み込みされた後でも残る。

## 切り分け

再発時に `/pbfont status` の `diag:` 行を見る。

| 見え方 | 意味 |
| --- | --- |
| `writes` が大きい / `matches=false` | リロードループ。原因はこちら。①②で止まるはず |
| `activations` は増えるが `writes` が 0〜1 | こちらは書いていない。別原因（コンソールの100MBメモリプール等）の巻き添え |

# 実測 5：diag の結果と、そこで見つかった別の不具合

```
enabled=true size=23 face="$(HANDWRITTEN_FONT)" style=6
in use: Gamepad
gamepad font now:  $(HANDWRITTEN_FONT)23 / 6
keyboard font now: $(BOLD_FONT) / 4
original gamepad:  $(STONE_TABLET_FONT)53 / 1     <-- 壊れている
original keyboard: $(STONE_TABLET_FONT)53 / 1     <-- 壊れている
diag: activations=2 writes=1
diag: lastWritten=$(HANDWRITTEN_FONT)23
diag: lastReadBack=$(HANDWRITTEN_FONT)23 matches=true
```

## ロード画面でのアドオン無効化 → こちらの原因ではない

- `activations=2` に対し `writes=1`。セッション1回だけの書き込みで、リロードループではない
- `matches=true`。**クライアントは記述子をそのまま返す**（正規化しない）ので、
  読み戻しガードは有効に機能する。1.3.0 で懸念した経路は実測で否定された
- ユーザー報告では**すべてのアドオンが不安定**になる。単一アドオンの問題ではなく、
  コンソールの共有メモリプール（100MB）側の話。PB's MiniMap の README に同じ症状の記述がある

## 「元の値」の退避データが壊れていた（1.3.1 で修正）

`original` に `$(STONE_TABLET_FONT)53`（＝このアドオンが書いた値）が入っていた。
改名時に旧 SavedVariables が引き継がれず、**石版53を適用した状態から「元の値」を取り直した**ため。
この状態では「元に戻す」を押しても石版53に戻り、素の状態には二度と戻れない。

### 判別方法（これが効く）

**クライアント本来のフォント記述子はサイズ成分を持たない。**
probe 0.1.0 の実測値は `$(GAMEPAD_MEDIUM_FONT)` / `$(BOLD_FONT)` で、いずれも素のフェイス名のみ。
`face|size` の形を書くのはこのアドオンだけ。

→ **`|` を含む記述子は「元の値」ではない**、と機械的に判定できる。

### 対処

- `CaptureOriginals` は `|` を含む値を退避しない。実測済みの stock 値にフォールバックする
- `HealOriginals` をロード時に実行し、すでに壊れている退避データを stock 値に直す（チャットに通知）
- `/pbfont stock` コマンドを追加。退避データを強制的に stock 値へ戻し、画面にも適用する

stock 値（probe 0.1.0 実測、エイリアスなので全言語で有効）:

| slot | font | style |
| --- | --- | --- |
| Gamepad | `$(GAMEPAD_MEDIUM_FONT)` | 4 |
| Keyboard | `$(BOLD_FONT)` | 4 |

player name="Luceda" title="至高なる征服者"

称号文字列は**区切り文字も `<<1>>` スロットも持たない素の文字列**だった。

# 実測 7：書体変更でまれに落ちる → CJKフォントの縁取り生成が原因の可能性

**ゲーム本体のフォント定義ファイルに答えが書かれていた。**
`esoui/fontstrings/japanese/defaultfontstrings_japanese.xml`（西欧版にも同じ注記）:

```xml
<!-- Split out from GAMEPAD_MEDIUM_FONT so we don't have to generate outlines for large CJK fonts.
This currently saves about 100 MB of memory, but is only useful as long as we only use
outlines with latin characters (usually numbers). -->
<String name="GAMEPAD_MEDIUM_FONT_LATIN" value="EsoUI/Common/Fonts/FTN57.slug"/>
```

**CJKフォントの縁取り生成 ≈ 100MB。コンソールのアドオン共有プール = 100MB。**

ZOS はこれを避けるために、わざわざ英数字専用のフェイス（`GAMEPAD_MEDIUM_FONT_LATIN`）を
分離している。こちらの「縁取り」設定は、まさに ZOS が避けた処理を日本語フォントに対して
要求している。しかも PB's MiniMap の README にあるとおり、
**アドオンの Lua フレームの下で起きた処理はアドオンのプールに計上される**。

→ 「書体変更時にまれに落ちる」「ロード画面で不安定」の説明として整合する。

## 対処（1.5.0）

- 縁取りのツールチップに警告を明記（英語・日本語とも）
- `/pbfont status` が `style=6 (FONT_STYLE_...)` のように**定数名を解決して表示**する。
  選択中のスタイルが本当に outline 系かどうかを実測で確認できる

## 次の切り分け

縁取りを「デフォルト」に戻したうえで、書体とサイズだけを変えて使う。
それで落ちなくなるなら、原因は縁取り（CJK outline 生成）で確定。

# 実測 8：再適用の書き込みそのものがアドオンを落としている

| 版 | ゾーン移動後の挙動 | 結果 |
| --- | --- | --- |
| 1.3.0（再適用なし） | フォントが素に戻る | **落ちない** |
| 1.5.0（再適用あり） | 書体が維持される | **落ちる** |

差分は再適用の書き込みのみ。→ **フォント書き込みのコストがアドオンのメモリプールに計上されている。**

PB's MiniMap の調査結果（アドオンの Lua フレームの下で起きた処理はプールに計上される）と、
ゲーム本体の「CJKフォントの縁取り生成 ≈ 100MB」というコメントの両方に整合する。

## コストの内訳（推定）

| 変更内容 | コスト | 根拠 |
| --- | --- | --- |
| **サイズ** | ほぼ無料と思われる | ESO のフォントは `.slug`（Slug＝GPUベクタ描画）。解像度非依存なのでサイズ別のアトラスを持たない。実際サイズ変更ではリロードも不具合も起きていない |
| **書体** | 高い | 未読み込みのフェイスをクライアントが構築する。UIリロードが発生することからも構築が走っているのが分かる |
| **縁取り** | 非常に高い（CJK） | ZOS 自身が約100MBと書いている |

ユーザーの現在設定は `$(HANDWRITTEN_FONT)`（＝`ESO_KafuPenji-M`、UIが他で使っていないCJK筆書体）
＋ `style=6`。**最も高くつく組み合わせ**になっている。

## 1.6.0 の対処

### ① 再適用を5秒遅らせる

ロード画面直後は全アドオンが同時に初期化していてプールが最も逼迫している。
そこにフォント構築を要求するのが最悪のタイミング。`zo_callLater` で5秒待つ。
代償は素のフォントが一瞬見えること。

### ② `/pbfont safe` を追加

サイズだけを残し、書体と縁取りをクライアント既定に戻す。
**クライアントにフォント構築をさせない唯一の構成**。

## 次の切り分け（1回で決まる）

`/pbfont safe` を実行してからゾーン移動を数回。

| 結果 | 意味 |
| --- | --- |
| 落ちない | 原因は書体・縁取りの構築コストで確定。サイズ変更専用アドオンとしては完全に成立する |
| まだ落ちる | 書き込み自体が高い。再適用を諦め、ゾーン移動でフォントが戻る挙動を受け入れるしかない |

# 実測 9：`/pbfont safe` でゾーン移動を繰り返しても落ちない → 原因確定

**サイズのみの適用は安全。書体・縁取りの再適用がアドオンを落としていた。**

| 適用内容 | ゾーン移動の反復 |
| --- | --- |
| サイズのみ（クライアント既定のフェイス・スタイル） | 落ちない |
| 書体・縁取りを含む（1.5.0 の挙動） | 落ちる |

これで一連の症状の説明がすべて揃った。

- サイズ変更でリロードも不具合も起きない … `.slug` は解像度非依存でサイズ別アトラスを持たない
- 書体変更でUIリロードが起きる … 未読み込みフェイスの構築が走っている
- 書体変更でまれに落ちる … その構築コストがアドオンプールに計上される
- ゾーン移動のたびに落ちる … ロード画面ごとにその構築を要求していた
- 全アドオンが不安定になる … プールは全アドオン共有

## 1.7.0 の設計変更

コストの違いに合わせて、**適用を2種類に分けた**。

| | 適用内容 | タイミング |
| --- | --- | --- |
| full | サイズ＋書体＋縁取り | セッション最初の1回のみ |
| cheap | サイズのみ（クライアント既定のフェイス・スタイル） | 以降のゾーン移動ごと |

これにより「フォント構築は1セッション1回」に抑えつつ、**文字サイズはロード画面を跨いで維持される**。
書体はセッション中の最初のロード画面まで有効で、以降はクライアント既定に戻る。

`reapplyFace`（既定オフ）をオンにすると 1.5.0 の挙動（毎回フル適用）に戻せる。
設定画面のツールチップに、実測に基づく危険性を明記した。

## 残る割り切り

書体はゾーン移動で失われる。これはクライアントがロード画面でフォント設定を破棄する仕様と、
コンソールのメモリプール制約の組み合わせによるもので、アドオン側では解消できない。
**このアドオンの安定した中核機能は「文字サイズ」である。**

# 実測 10：落ちる書体の特定（1.8.0）

PS5・日本語クライアントで、以下の4つを選ぶと落ちると報告された。

| 選択肢 | 日本語版の実体 | UIでの使用 |

  チャットで通知する。**除外リストではなく `addon.faces` との照合**なので、
  将来フェイスを増減しても自動的に追随する
- 再適用の待ち時間を 5秒 → 3秒

# 1.9.0：再適用の待ち時間を 1 秒に

5秒 → 3秒 → **1秒**。

待ち時間はもともと「ロード画面直後にフェイス構築を要求しない」ための保険だった。
1.7.0 で **フェイスを書くのはセッション最初の1回だけ**になり、ゾーン移動後の再適用は
「クライアントが既に持っているフェイスにサイズを載せる」だけでフォント構築が発生しない。

→ 待ち時間が守るものはほぼ無くなった。短くして文字サイズの適用遅れを目立たなくする。

残る守備範囲はセッション最初のフル適用のみ。
**もし今後また落ちるなら、ゾーン移動時ではなくログイン時に落ちるはず**であり、
そのときは待ち時間ではなくフル適用のタイミング自体（明示コマンド化など）を見直す。

# 版数について

この文書に出てくる `0.1.0` 〜 `1.9.0` は**すべて開発中のテストビルド**の番号で、
症状の切り分けのために刻んだもの。公開版としての最初のリリースは **1.1.0**。

したがって「1.3.0 で〜」「1.7.0 で〜」といった記述は開発経緯の記録であり、
配布されている版数とは対応しない。コード中のコメントからは、
現在の版数より大きい番号を指してしまい誤解を招くため、具体的な番号を外してある。
